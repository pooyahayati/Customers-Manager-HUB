# ADR-015: S3-Compatible Object Storage and PostgreSQL pgvector RAG

**Status:** Accepted  
**Date:** 2026-09-07  
**Supersedes:** ADR-006 for backend selection

## Context

Milestone 9 implements knowledge-file storage, ingestion and retrieval. The project already requires a vendor-neutral S3 storage boundary and PostgreSQL + pgvector for initial vector search.

ADR-006 deliberately deferred selecting a self-hosted object-storage backend until this milestone. That decision was necessary because the previously assumed MinIO Community prebuilt path was no longer a suitable maintained default for the commercial/self-hosted baseline.

The project needs:

- an S3-compatible contract usable with AWS S3 and compatible providers;
- one maintained, lightweight self-hosted development reference for Docker Compose;
- no object-storage vendor concepts in knowledge business logic;
- provider-independent embeddings through the existing AI Gateway;
- strong tenant scoping and source provenance;
- minimal operational complexity.

## Decision

### Object storage

- The application storage API remains **S3-compatible and vendor-neutral**.
- Python infrastructure uses a canonical S3 storage adapter; knowledge modules depend on an internal storage contract rather than a vendor SDK surface.
- Docker Compose uses a pinned **SeaweedFS** release in single-node S3 mode as the self-hosted development/reference backend.
- SeaweedFS is not a product-domain dependency and is not required for deployments that configure AWS S3 or another compatible service.
- S3 bucket, endpoint, region and credentials are environment configuration. Credentials never enter model context or client responses.
- Object keys are generated by trusted application code from UUIDs, not from user-controlled paths.

### Vector storage and retrieval

- PostgreSQL remains the source of truth for knowledge metadata, chunks and retrieval traces.
- Embeddings are stored with PostgreSQL `pgvector`.
- M9 uses exact cosine-distance search with strict tenant, Agent→Knowledge permission, source-ready and embedding-signature filters.
- Embedding provider/model/dimension are stored with chunks and sources so different vector spaces are never compared silently.
- No separate vector database, search cluster or reranking service is introduced in M9.

### Asynchronous ingestion

- Knowledge ingestion uses a dedicated Redis Stream consumer group and the existing worker process.
- A separate worker service is not introduced; the existing worker consumes both channel and knowledge jobs.
- Parsing, chunking, object retrieval and embedding run outside inbound channel webhook lifecycles.

## Alternatives considered

### MinIO Community as the Compose default

Rejected. The community repository/distribution path is no longer an appropriate maintained prebuilt default for this project. The S3 contract remains compatible with MinIO-derived or commercial deployments if an operator intentionally chooses them.

### AWS S3 only

Rejected as the sole default because the product explicitly supports self-hosted Docker deployment and local integration testing.

### Garage

Viable S3-compatible self-hosted storage, but its cluster/bootstrap model adds more setup than needed for the single-node development reference used in M9.

### Dedicated vector database

Rejected for M9. PostgreSQL + pgvector is already part of the deployment image and satisfies initial tenant-scoped retrieval without another stateful service.

### OpenSearch/Elasticsearch hybrid retrieval

Deferred. It adds infrastructure and operational complexity before corpus scale or relevance measurements justify it.

## Consequences

- `compose.yaml` gains one object-storage service and persistent volume.
- M9 adds S3, pgvector Python, PDF/XLSX parsing and multipart dependencies only because they are directly required by implemented behavior.
- Self-hosted development has a complete file-storage path without binding production deployments to SeaweedFS.
- Exact vector search is intentionally simple; ANN indexes or hybrid/reranking can be added later behind the retrieval contract.
- Changing the embedding task profile can create a new vector space. Existing sources must be reindexed before they are searchable with the new signature.
- Object-storage backup/HA and advanced vector-scale tuning remain M15 concerns.

## Follow-up implications

- M9 tests must prove S3 adapter behavior independently from SeaweedFS and also run one real Compose/storage integration path.
- M15 must document production object-storage TLS, backup/restore, credential rotation and egress/network policy.
- If a future ADR selects a different self-hosted reference backend, no knowledge-domain migration should be required because object storage remains S3-compatible.
